BACKGROUND
pick6.draftkings.com server-renders its data as a React Router v7 stream payload
embedded in the initial HTML (window.__reactRouterContext.streamController.enqueue("...")).
scripts/pick6_refresh.py already correctly extracts and decodes this into a flat
indexed array and resolves "_N"-style keys back to real field names (see
_extract_stream_payload, _build_idx_to_name, _resolve_refs). This part works —
confirmed live, real 200 responses, real ~590KB-1MB payloads, stat_names and
pickable_id_key resolve fine.

THE BUG
In fetch_sport_props(), player_names ends up empty. The code assumes a single
dict shape carries both the player's dkId AND their name/fullName together
(_build_lookup_tables looks for one dict with both), but a debug capture on a
real MLB run showed dkId-carrying dicts that DON'T have a name/fullName field
alongside it — e.g. {"_1498": 1499, "_1500": 1501} (dkid_key=1498, but no name
key present in the same dict). So dkId and player name are very likely two
SEPARATE dict shapes in the real payload, correlated via some other shared key
(possibly pickableId, possibly something else) rather than co-located.

Also worth checking: the diagnostic debug logging in this function is currently
hardcoded to `if sport == "MLB":` only — so it's unknown whether NBA/NFL/NHL/
WNBA/SOCCER/UFC/PGA+TOUR/NASCAR have the identical bug or something different.
The fallback `player_names.get(dk_id, f"dkId_{dk_id}")` means those sports may
currently be silently producing placeholder names like "dkId_12345" instead of
real ones, or may be failing entirely — not yet confirmed either way.

Separately: pick6_props_live.json (the Gist file the app actually reads, via
fetchers.py's fetch_pick6_props_from_gist()) has never once existed in the Gist,
despite this workflow showing "success" repeatedly. main()'s own logic explains
this IF all_props ends up genuinely empty (it deliberately returns exit 1 rather
than push an empty file) — but if the placeholder-name theory above is right,
all_props might NOT be empty, which would mean push_to_gist() itself is failing
silently for a different reason. Please check the actual GH Actions run logs
directly (you have real log access, unlike a sandboxed agent) to see which case
it actually is.
